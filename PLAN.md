# План: клиент Яндекс Книги для Amazon Kindle

Документ описывает архитектуру, стек и этапы разработки приложения-клиента
сервиса **Яндекс Книги** (Bookmate/Букмейт) для устройств **Amazon Kindle**
(e-ink, jailbroken).

Источники, на которых основан план:
- API-обёртка: https://github.com/stepan163s/yandex-book-api
- Kindle dev: https://kindlemodding.org/kindle-dev/index.html

---

## 1. Цель

Дать возможность на Kindle:
1. Войти в аккаунт Яндекс Книги (OAuth).
2. Просматривать свою библиотеку, полки, историю и поиск.
3. **Читать текстовые книги** на e-ink экране с нормальной пагинацией,
   шрифтами и синхронизацией прогресса.
4. (Опционально, вторая очередь) слушать аудиокниги.

Аудиокниги на e-ink Kindle — низкий приоритет: у большинства моделей нет
динамика/аудиовыхода, а CPU слаб для декодирования. Основной фокус — **текст**.

---

## 2. Критические ограничения и риски (прочитать первым)

### 2.1. Доступ к контенту книг — главный риск ⚠️
Библиотека `yandex-book-api` покрывает **метаданные**: профиль, библиотеку,
полки, отзывы, статистику, поиск (GraphQL). Но в ней **нет** задокументированных
методов для скачивания **текста книги** (EPUB/FB2/главы) или **стрима
аудио**. Контент Яндекс Книг защищён и отдаётся приложениям по отдельному,
недокументированному протоколу чтения (последовательность документов-глав,
которые ридер собирает на лету; ср. community-проект `bookmate_downloader`).

**Вывод:** ядро приложения — reader — упирается не в UI, а в получение
контента. Это нужно исследовать и решить **до** начала полноценной разработки
(см. Фаза 0). Без решения этого вопроса проект сводится к «просмотрщику
метаданных».

**Правовой аспект:** обход DRM/ToS сервиса — зона риска. Приложение должно
работать только с легально доступным пользователю контентом (его подписка/
покупки), под его собственным токеном. Это надо явно зафиксировать.

### 2.2. Ограничения устройства Kindle
- **CPU/RAM:** слабый ARM, мало памяти. Тяжёлые рантаймы (полноценный Python
  со стеком aiohttp/GraphQL) на устройстве — нежелательны.
- **glibc старая:** нативные бинарники надо кросс-компилировать под целевой
  toolchain (Meson + кросс-файл), нельзя просто взять сборку с десктопа.
- **E-ink дисплей:** медленное обновление, оттенки серого, гостинг. Никаких
  анимаций/скролла — только постраничное обновление, продуманный partial/full
  refresh.
- **Ввод:** тач и/или аппаратные кнопки в зависимости от модели. UI должен
  работать крупными зонами нажатия.
- **Сеть:** Wi-Fi нестабилен, экономия трафика/офлайн-кэш обязательны.
- **Jailbreak + KUAL:** для запуска стороннего кода нужен джейлбрейк,
  hotfix (переживает OTA) и KUAL (лаунчер кастомных приложений).

### 2.3. Аутентификация
Токен Yandex OAuth (`y0_...`) получается через браузерный флоу
(`oauth.yandex.ru/authorize?response_type=token&client_id=...`). На e-ink
устройстве полноценный OAuth-браузер неудобен → **логин выносим на сторону
бэкенда/десктопа**, на устройство передаётся уже готовый токен.

## 3. Целевые устройства

- Приоритет: современные Kindle на Linux с возможностью джейлбрейка
  (например, Paperwhite / базовые модели актуальных поколений).
- Договориться о конкретной модели/прошивке заранее — от неё зависит toolchain,
  разрешение экрана и способ ввода.

---

## 4. Рекомендуемая архитектура: тонкий клиент + бэкенд-прокси

Ключевая идея — **не тащить Python/GraphQL/OAuth/DRM-логику на устройство**.
Вынести всё тяжёлое на сервер (или десктоп-компаньон), а Kindle оставить
тонким клиентом.

```
┌─────────────────────────┐        HTTPS / OPDS         ┌──────────────────────┐
│   Kindle (e-ink)        │  ◀──────────────────────▶   │   Backend-прокси      │
│                         │                             │   (Python)            │
│  Reader / UI-клиент     │                             │                       │
│  - каталог (OPDS)       │                             │  yandex-book-api      │
│  - чтение EPUB          │                             │  + резолвер контента  │
│  - кэш/офлайн           │                             │  + OAuth-хранилище    │
└─────────────────────────┘                             │  + конвертер в EPUB   │
                                                        │  + OPDS-сервер        │
                                                        └──────────┬───────────┘
                                                                   │
                                                          ┌────────▼─────────┐
                                                          │  Яндекс Книги API │
                                                          │  (REST + GraphQL) │
                                                          └──────────────────┘
```

**Backend-прокси (Python) отвечает за:**
- Хранение и обновление OAuth-токена пользователя.
- Вызовы `yandex-book-api`: библиотека, полки, поиск, метаданные, прогресс.
- **Резолв контента:** получение глав книги из протокола чтения Яндекса и
  сборка их в валидный **EPUB** (с обложкой, оглавлением, метаданными).
- Отдачу каталога в формате **OPDS** и файлов EPUB по HTTP.
- Синхронизацию прогресса чтения обратно в Яндекс.
- Кэширование, чтобы не дёргать Яндекс на каждый запрос.

Это резко упрощает клиента: на устройстве не нужен ни Python, ни знание
внутренних эндпоинтов Яндекса.

## 5. Варианты клиента на устройстве

### Вариант A (рекомендуется для MVP): KOReader + OPDS
**KOReader** — де-факто стандартный ридер на джейлбрейкнутых Kindle. Уже решает
пагинацию, шрифты, словари, темы, refresh e-ink, поддерживает **OPDS-каталоги**
и плагины (Lua).

- Бэкенд отдаёт OPDS-каталог библиотеки Яндекса → пользователь листает и
  скачивает книги как EPUB прямо в KOReader.
- Синхронизацию прогресса и «моя библиотека / полки / поиск» можно оформить
  **плагином KOReader на Lua**.
- Плюсы: минимум разработки на устройстве, готовый качественный ридер,
  быстрый выход MVP.
- Минусы: UX ограничен рамками KOReader; кастомный брендинг/аудио — сложно.

### Вариант B: нативное приложение (KUAL + C/C++)
Полностью своё приложение под KUAL, нативная сборка C/C++ через **Meson** с
кросс-toolchain, прямая работа с framebuffer/вводом.
- Плюсы: полный контроль UX, возможность аудио, свой брендинг.
- Минусы: очень трудоёмко — пагинацию и рендер текста придётся делать/портировать
  самому; долгий путь до MVP.

### Вариант C: Python + web-технологии (framework типа kapps)
Приложение на Python + web-UI поверх встроенного вьюера.
- Плюсы: быстрее прототипировать UI.
- Минусы: производительность на слабом железе, зависимость от рантайма; для
  чтения книг всё равно нужен нормальный ридер.

**Рекомендация:** начать с **Варианта A** (KOReader + OPDS + Lua-плагин) для
MVP чтения текста. К **Варианту B** переходить только если понадобится
кастомный UX или аудио, которых KOReader не покрывает.

## 6. Интеграция с API Яндекс Книг

Что даёт `yandex-book-api` (используем на бэкенде):

**Без авторизации:** `get_book`, `get_user_books`, `get_user_audiobooks`,
`get_user_quotes`, `get_user_bookshelves`, `book_impressions`.

**С токеном (≈21 метод):** `get_my_library` (пагинация), `add_book`,
`remove_book`, `get_profile`, `get_my_bookshelves`, `get_series_following`,
`get_reading_achievements`, `get_sync_state`, `test_token` и др.

**Поиск:** через GraphQL-endpoint.

**Модели:** Book (uuid, title, annotation, cover, authors), Image, Person,
LibraryCard (progress 0–100%, state pending/reading/finished), User.

**Чего НЕ хватает и надо решать самим (Фаза 0):**
- Скачивание текста книги (эндпоинты протокола чтения → сборка EPUB).
- Стрим аудио (для Варианта B/аудио-очереди).
- Точный формат GraphQL-запросов поиска (уточнить по исходникам библиотеки).

---

## 7. UI/UX под e-ink (для кастомного клиента, Вариант B/C)

- Только постраничные экраны, без скролла и анимаций.
- Крупные тач-зоны / привязка к аппаратным кнопкам.
- Продуманный refresh: partial update для навигации, full refresh периодически
  против гостинга.
- Высокий контраст, крупный шрифт, монохром-дружественные обложки (dithering).
- Экраны MVP: Библиотека → Карточка книги → Читалка; Поиск; Настройки/логин.

---

## 8. Данные, кэш, офлайн

- Бэкенд кэширует метаданные и уже собранные EPUB.
- На устройстве — локальное хранилище скачанных книг и позиции чтения.
- Синхронизация прогресса: устройство → бэкенд → Яндекс (`sync_state`), с
  разрешением конфликтов «последний по времени выигрывает».
- Экономия трафика: докачка, ETag/кэш-заголовки на OPDS/файлах.

## 9. Этапы разработки

### Фаза 0 — Исследование осуществимости (блокирующая) 🔬
- Разобраться, как приложение Яндекс Книг получает текст книги; можно ли под
  токеном пользователя воспроизвести это и собрать EPUB.
- Прояснить правовые/ToS-рамки; зафиксировать, что работаем только с легальным
  доступом пользователя.
- **Решение go/no-go**: если контент недоступен — переопределить продукт как
  «просмотрщик библиотеки + метаданные» без чтения.

### Фаза 1 — Backend-прокси (MVP-фундамент)
- Обёртка над `yandex-book-api`, хранение токена, вызовы библиотеки/поиска.
- Резолвер контента → сборка EPUB (по итогам Фазы 0).
- OPDS-сервер + отдача EPUB.

### Фаза 2 — Клиент MVP (Вариант A)
- Джейлбрейк/KUAL/KOReader на тестовом устройстве.
- Подключение OPDS-каталога бэкенда, чтение EPUB.
- Lua-плагин: «моя библиотека», поиск, синхронизация прогресса.

### Фаза 3 — Полировка
- Офлайн-кэш, обложки под e-ink, устойчивость к обрывам Wi-Fi.
- Логин-флоу компаньона (получение токена вне устройства).

### Фаза 4 — Опционально
- Нативное приложение (Вариант B) для кастомного UX.
- Аудиокниги (только для моделей с аудио).

## 10. Открытые вопросы (уточнить у заказчика)

1. Конкретная модель Kindle и версия прошивки?
2. Нужны ли аудиокниги, или только текст?
3. Приемлема ли схема с внешним бэкендом-прокси (нужен хостинг), или клиент
   должен быть полностью автономным на устройстве?
4. Правовые рамки: подтверждаем работу только с легальным доступом пользователя?
5. Достаточно ли KOReader как читалки (Вариант A), или обязателен кастомный
   брендированный UI (Вариант B)?

## 11. Первый шаг

Начать с **Фазы 0**: техническая разведка получения контента книги под токеном
пользователя. От её результата зависит, будет ли это полноценный ридер или
просмотрщик библиотеки — поэтому это должно быть сделано до любой другой работы.
